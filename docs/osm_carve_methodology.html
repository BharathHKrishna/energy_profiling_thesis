The core idea: pay the scan cost once, not per coordinate

osmium extract given a batch config with N bounding boxes does one pass over the source file and pulls out all N tiles from that single scan. The dominant cost is reading through the planet file — planet-latest.osm.pbf, 93.4 GB, deliberately the full unfiltered planet ("every tile holds 100% of OSM — nothing lost. The filtered pbf is available but drops tags") — not how many bboxes are being extracted from it. So the entire point of osm_carve as a separate, batched, upfront stage is to pay that ~93 GB scan cost once across every selected coordinate, instead of once per coordinate inside stream.

If stream's 4 parallel workers each tried to carve their own coordinate's tile live instead, up to 4 simultaneous full scans of the same 93 GB file could be running at once — no correctness issue, pure waste. This isn't a correctness-driven sequencing (unlike BORE's ESA-before-GHSL fail-fast filter order) — it's a raw cost-amortization argument.

Why chunked at 450, not one shot for any N

CHUNK = 450 # osmium extract caps at 500 bboxes/config -> chunk under it

osmium extract has a hard ceiling of 500 regions per config file. 450 leaves headroom under that cap. Practical consequence: the number of full-planet scans needed is ceil(N / 450), not N — carving 18 coordinates costs the same one scan as carving 450 would; carving 10,000 costs 23 scans, not 10,000.

Linear extrapolation from a single-chunk measurement to 23 chunks — not verified at that chunk count yet. One open question noted but not resolved: this machine had ~91GB of the ~93GB planet file sitting in OS page cache after repeated same-day runs (125GB total RAM) — later chunks in a real 23-chunk run might run faster than the ~850s/chunk average if the file stays cached, but this is a shared multi-user server where cache eviction from other users' workloads is a real risk, so the 5.4h figure is treated as the conservative estimate, not a guaranteed ceiling.

The live-fallback path (used by stream, not osm_carve itself)

FIXED 2026-08-10read_local_osm()

scripts/extractors/osm_extractor.py::read_local_osm() is the shared reader every downstream OSM consumer calls (feature extraction, map rendering, the demand-score OSM gate). Fast path: read the pre-carved 512m tile for this coordinate, ~5-12ms. If no tile exists, it falls back to a live osmium extract against the full 93GB planet file for just that one coordinate — correctness-preserving, but ~800-900s slow (the same cost as a whole batch, for one point).

FAST: _tile_name(lat, lon) -> os.path.exists(tile) -> read (~5-12ms) FALLBACK: tile missing -> live osmium extract on the full 93GB planet (~800-900s)

Real bug found and fixed this session: the demand-score OSM gate (osm_offline.py::extract_osm_use()) reconstructed its tile-lookup filename from (min_lat+max_lat)/2 after each bbox edge had been rounded independently to 6 decimal places by generate_bbox(). For one coordinate (Dense Urban, lat 25.311145) that round-trip landed on 25.31115 instead of the carved tile's actual 25.31114 — a one-digit miss that silently triggered the ~20-minute live fallback instead of a 5ms local read, even though the correctly-carved tile was sitting right there on disk the whole time. Confirmed via direct measurement: that single coordinate accounted for 1218 of a 1260-second stage total; all other 17 coordinates in that run were instant.

Fix: read_local_osm() now accepts optional lat=None, lon=None parameters — when the caller has the original, unrounded coordinate (as extract_osm_use() always does, since it's a direct function argument), it's used directly for the tile filename instead of being reconstructed from bbox-edge rounding. Verified fixed: the same coordinate that took 1218s now resolves in 0.017s.
