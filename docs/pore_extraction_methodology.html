The streaming architecture — two pools, not one

PROCESS POOL N_WORKERS=4 — extract (7 sources) + demand/demand_score + 4 map renders, all CPU/IO-heavy work (rasterio, GEE calls, matplotlib, an OSM subprocess). THREAD POOL CAPTION_WORKERS=6 — the Groq API call, network-I/O-only, releases the GIL while waiting on the response.

Critically, a coordinate's caption is submitted the moment its own extract+maps future completes — via as_completed() inside the loop, not after the whole batch finishes. This replaces an older design where features, maps, and captions were three sequential batch stages with hard barriers between them.

with ProcessPoolExecutor(max_workers=N_WORKERS) as pool: futures = {pool.submit(_extract_and_maps_worker, t): t for t in tasks} for future in as_completed(futures): features, maps_ok, maps_err = future.result() if features is not None: _append_feature_row(features) # incremental, resume-safe _submit_caption(features) # fires immediately, doesn't wait for the batch
Resume-safety: coordinates already in pore_features.csv skip re-extraction, but still get checked for a missing caption up front — they don't wait behind the current run's new extractions.

Null-contract convention

Absent data means the dict key is absent, never a sentinel value like 0 or NaN written directly by extraction code — a stratum with no OSM buildings looks different from a stratum where the OSM read itself failed, and a coordinate over open water genuinely has no climate data rather than a fabricated zero. The one deliberate exception: osm_building_count=0 is a real, meaningful zero (a coordinate can genuinely have zero buildings), not an absence.

When features are read back through pandas (pore_features.csv → DataFrame), an empty cell becomes NaN, not the original absent-key state — _clean_row() converts float NaN back to None for anything reloaded this way.

Demand — two pieces, both derived, neither re-fetches data

CHANGED 2026-08-10heating_MWh / cooling_MWh — now exactly one, never both

demand_extractor.py::demand_from_features() computes annual heating/cooling energy demand from already-fetched GHSL (built surface, height) and climate (HDD18, CDD24, mean temp) values — no new GHSL read, no new GEE call.

Previous behavior: both heating_MWh and cooling_MWh were always computed and returned together, reasoning that a single annual mean can mask real heating AND cooling need on different days within the same year.

Current behavior, by explicit instruction: exactly one value is reported, chosen by demand_regime (mean annual temp vs the same 18°C/24°C thresholds already used for HDD/CDD):

mean_temp < 18°C → "heating" regime → heating_MWh only 18°C ≤ mean_temp ≤ 24°C → "comfort" regime → neither key (both NaN when read back) mean_temp > 24°C → "cooling" regime → cooling_MWh only mean_temp unavailable → regime = None → neither key

Verified live across all 4 cases with real numbers, e.g. heating regime → {'heating_MWh': 222.2} with no cooling_MWh key at all — not a zero, an absence.

demand_score / demand_tier — the separate 0-100 score

demand_score.py::demand_score_for_coord() — a different, deliberately single-cell (not the notebook's validated 9-cell/3×3-neighborhood-mean) formula, ported from energy_demand_formula.ipynb:

softceil( sqrt(built) * viirs^0.2 * max(height,4)^0.3 / 5 * osm_gate, knee=72, span=28, tau=37 ) tiers: HIGH ≥ 65, MID-HIGH ≥ 45, MID ≥ 25, LOW < 25

The osm_gate term is a second, separate local OSM read (osm_offline.py::extract_osm_use(), landuse-dominance + power-generation-override multiplier) — distinct from the main OSM feature extraction earlier in the same pass, cheap since OSM is fully offline now. This is the exact function that had the tile-lookup rounding bug documented in docs/osm_carve_methodology.html.

Both heat/cool MWh and demand_score/tier are computed inside extract_all_features() as steps 6b and 7b, and both are cited in groq_caption.py's prompt construction. "Energy demand" unqualified refers to this score/tier, never the physical heat/cool MWh formulas — a terminology distinction established early and enforced throughout the project.

Previous behavior: the worker fetched OSM elements once, then gated ALL 4 maps behind it — if elements: [render all 4] else: skip all 4, maps_ok=False. Confirmed live: 2 of 18 coordinates in one run lost all 4 maps this way, logged only as a one-line "OSM fetch returned empty" warning.

Why this was wrong: traced through the actual code — generate_single()/render_ghsl_segmap() don't take an elements parameter at all, and render_detection_panels()/ render_ghsl_det() both default to elements=None and handle an empty list fine (zero OSM building overlay, but Microsoft Buildings — a separate data source — still renders independently). An empty OSM fetch is a legitimate, if sparse, result, not a failure.

Fix: all 4 maps are now always attempted; a genuinely empty OSM fetch produces a soft warning log, not a skip. Verified live: the two previously-broken coordinates got complete map sets on the next run with no other change.

The ragged-CSV bug

FIXED 2026-08-10_append_feature_row() header drift

The incremental per-coordinate CSV writer grows its shared feature_fieldnames list as later coordinates introduce optional keys earlier ones lacked — expected, given the null-contract convention means different strata legitimately populate different optional fields (a coordinate with no climate coverage simply lacks those keys). The bug: the on-disk header was written once, from the first coordinate's narrower key set, and never rewritten as the fieldname list grew.

row 0 (header): 46 columns row 1: 46 columns row 2: 51 columns ← already wider than the header ... row 18: 54 columns ← pandas.read_csv: "Expected 46 fields, saw 54"

Fix: a normalization pass now runs automatically at the end of every stream run. Since feature_fieldnames only ever grows by appending (never reorders/removes), every row's on-disk width is guaranteed to be a prefix of the final fieldname list in write order — safe to re-pad every row to the final column count and replace the stale header in one rewrite pass.
